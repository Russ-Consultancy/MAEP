# aep-client (operator)

This is the **operator's source folder** for the AEP wrapper. It contains the
source code for the `aep-client.exe` binary that ships to clients. Clients
never see this folder — they only receive `aep-wrapper/`.

```
aep-client/                   <- you are here
├── server.js                 wrapper source (Express + JWT + composite token + activity log)
├── assets.js                 AUTOGENERATED: base64 of browser/*.js, bundled into the binary
├── browser/                  plain source for the three browser scripts (editable)
│   ├── aep-auth.js
│   ├── aep-guard.js
│   └── aep-signin.js
├── rebuild-assets.ps1        re-encodes browser/*.js -> assets.js
├── build-sea.ps1             produces a Node SEA single-file binary
├── package.json              build deps (esbuild, postject)
├── config.example.json       template for config.json (the only file the client edits)
├── .gitignore
├── dist/                     output of `npm run build:*` (the binaries)
└── node_modules/             dev only
```

## How the binary is built (Node SEA)

`aep-client.exe` is a **Node Single Executable Application** (SEA) — the
official Node.js 24+ feature. The build process:

1. `rebuild-assets.ps1` refreshes `assets.js` from `browser/*.js` (base64).
2. `esbuild` bundles `server.js` + `assets.js` + `express` + `cors` +
   `jsonwebtoken` into a single self-contained `sea-bundle.cjs`
   (no runtime `require()` of `node_modules`).
3. `node --experimental-sea-config sea-config.json` turns that bundle
   into a SEA blob.
4. The build copies `node.exe` to `aep-client.exe` and `postject` injects
   the blob as a `NODE_SEA_BLOB` resource and flips the SEA sentinel fuse.

The result is a single `.exe` that **is** a regular `node.exe` with a
script blob appended. It is not a packer, has no virtual filesystem, and
is therefore not flagged by Symantec / Defender / most AV products.

## Edit-and-build cycle

1. Edit a script in `browser/` (or `server.js`).
2. Run `npm run build:win` (or `:linux` / `:macos`).
3. Copy `dist/aep-client.exe` into `../aep-wrapper/`.

The binary now serves the three scripts at `/aep-{auth,guard,signin}.js`,
so the consuming app's `<script src="http://<host>:<port>/aep-guard.js">`
picks up the new version on next page load — no file copy to the app needed.

## Test (without building)

```powershell
cd aep-client
copy config.example.json config.json
# edit config.json (brokerOrigin, appId, appName, brokerActivitiesUrl, …)
node server.js
```

## What the binary serves

| Path | Method | Response |
|---|---|---|
| `/aep-auth.js` | GET | the `aep-auth.js` script (vanilla helper, sets `window.AepAuth`) |
| `/aep-guard.js` | GET | the `aep-guard.js` script (invisible `<aep-guard>`) |
| `/aep-signin.js` | GET | the `aep-signin.js` script (visible `<aep-signin>`) |
| `/api/auth/sso-login` | POST | `{access_token, compositeToken, token_type, expires_in, expires_at, username, role, company, lastLogin}` |
| `/api/auth/me` | GET | JWT claims if `Authorization: Bearer <token>` is valid |
| `/healthz` | GET | `{ok: true, appId, name}` |

CORS is locked to the broker origin. Cross-origin `<script src="…">` from
consuming apps is allowed (browsers don't enforce CORS on scripts).
